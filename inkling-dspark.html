4. The five n-gram modes

None of them runs a model. Each looks up the slot's recent tokens in some store and proposes what followed last time. None produces q, so the target always checks them by token matching. Their process() hooks are empty.

serverShared input: the slot's token history and id_last.
key = the last n tokens, ending in id_last

ngram-simple

hostUses: the history itself, no stored state.

Scans backwards for the latest earlier copy of the key and proposes the m tokens after it.

ngram-map-k

stateUses: a per-slot list of keys seen in the history, found through a hash index of 218 entries.

Proposes the m tokens after the matched key. Keys only, no value statistics.

ngram-map-k4v

stateUses: the same key list, plus up to 4 distinct continuations per key with counts.

Needs min_hits key hits. Proposes the most frequent continuation unless the others together are too close. accept(k) records how much of it the target took.

ngram-mod

stateUses: one hash table of 4 M entries shared by all slots: hash of n tokens → next token.

Proposes token by token, chaining lookups up to n_max. Resets when a quarter full, or after five rounds in a row with under 25% accepted.

ngram-cache

stateUses: three count tables for n-grams of length 1 to 4: the current context, a dynamic file from earlier runs, and a static corpus file.

Proposes up to 8 tokens, each needing enough count and share. The static table checks the others. The context counts are merged into the dynamic file at exit.

Why this needed a change

Before the PR the Inkling 2 target graphs filled no tap slots at all, so DFlash feature extraction had nothing to read. The fix points existing result slots at tensors the target already computes. It adds feature extraction and transport to the existing target computation.

The visit counter matters because the looped model shares weights between passes. A tap named by physical layer would be ambiguous: the same layer runs several times with different inputs.

Why a position-tagged ring

The head needs the fourth-mixture row of the last committed token. The most recent injection is a verify batch, and its tail can hold rows for draft tokens the target then rejected. "The newest row" would be wrong after any rejection.

The driver reads the row for position pos0 − 1 and checks the stored tag. If the tag does not match, the slot does not draft this round. That row is always the last row the target accepted, because pos0 is where the target's own replacement or bonus token will go.

LiliCorr already had exactly this ring as private members. The PR moves it into the DFlash base class, lets any head opt in by allocating it, and also fills it after device-row injection, which LiliCorr never used. speculative.cpp:1575-1593 speculative.cpp:1883-1901

Why the full block, one slot per call

The sidecar was trained on one anchor plus seven masks under non-causal attention. Every row can change every other row, so a shorter block is a different input. Stock DSpark sends only as many rows as it wants drafts. The Inkling driver always sends eight and reads fewer.

The window is anchor-relative: the existing block_uniform switch gives every block row the first row's mask. The loader adds 1 to the stored window of 1024 because the mask excludes distances greater than or equal to its size, and the trained window covers the anchor plus 1024 positions before it.

The context decode refuses anything but this shape when the first row carries side state: exactly 8 rows, one sequence, token rows only, outputs on rows 1 … D. One slot per call keeps that invariant simple and costs some multi-slot batching.

The law that is reported is the law that is sampled

ticket = integer in [0, 2^24), uniform id = the ID whose interval contains ticket q[id] = interval width / 2^24 => P(id is drawn) = q[id], exactly

Rejection sampling is exact only if q is the true probability of the draft's draw. Here both come from the same integer endpoints, so a correctly executed graph reports the probabilities it used.

q approximates the temperature softmax; it is not equal to it. Widths are whole numbers of tickets, so a token with a very small probability can get zero tickets and q = 0. It can then never be drafted, and the verifier's residual gives it all of p. Under rejection sampling, changing q can change acceptance and seeded output sequences while preserving the target distribution.

Why integers. A float32 running sum over 200058 values depends on the order a backend adds them, and loses the tail next to a large head. Each of the three digit sums stays inside the range where float32 represents integers exactly, so any summation order gives the same counts.

CPU A stress row with 0.995 on the first ID and the rest spread evenly gave q0 = 0.9949985743, qlast = 0, total variation 0.0029 from the ideal softmax, and 83899 IDs with non-zero mass.

unverified The endpoint rounding still passes through a backend softmax and a division. Endpoints may differ between backends; the equality of draw and q does not depend on that, but no accelerator run has checked either.

What this fixes in the accounting

  • One draw per emitted proposal. Warm-up graphs, greedy slots, skipped slots and the unrequested tail of the block consume nothing.
  • A rejected suffix still spent its draws. The generator is committed when the block is read. Rolling back target tokens does not roll back the draft RNG, so the next round uses fresh tickets.
  • Same request, same stream. The per-request reset makes two identical seeded requests on one slot draft the same tokens.
  • The row q is dense and ID-ordered. The driver builds each verifier row as entry j = { id j, probability qj }. That is the layout the new direct lookup in the verifier tests for.

7. Why the existing paths were not enough

Plain DFlash

  • It projects taps through one fc matrix and reuses each layer's token-side K and V weights. The Inkling sidecar has neither fc nor an encoder norm. It has four learned mixtures and separate context K/V weights.
  • Its rows are picked independently. The Inkling head needs the previous chosen token and a state.
  • It returns top-k 10 candidates, never a distribution the verifier can use.

dflash.cpp:250-266 speculative.cpp:1318-1398

Stock DSpark

  • Shapes. It expects markov_w1 at tokenizer width, a W2 that maps the latent straight to vocabulary logits, and a joint input of n_embd + 2 × rank. The sidecar stores W1 at padded width, has no W2, maps the latent back to hidden space, and feeds 2 × n_embd + 2 × rank.
  • Feedback. Its chain feeds back argmax inside the graph, and its driver takes the top candidate. A sampled token never enters the chain, so any q read from it would be conditioned on the wrong prefix once a draw differs from the argmax.
  • Block length. It shortens the batch to the draft length. The Inkling block needs all eight rows.

A registered backend sampler alone

  • A registered chain is applied once to the graph's final logits tensor, after the model graph is built. It cannot sit between link i and link i + 1 of a recurrence, and the Inkling block graph publishes no logits tensor for it to read.
  • The head needs the selected ID as a tensor for the next W1 lookup. So the graph does the selection itself and writes into the same result slots a chain would fill.
  • The driver turns the base class's backend chain off for this head.
  • The predecessor report also found that a float32 cumulative sum over a 200058-wide row can leave the tail with zero-width bins while still reporting non-zero q for it. A draw whose reported q disagrees with its real probability breaks rejection sampling. That is why the PR draws on an integer grid. unverified This page did not rerun that calculation.

Host-only recurrence

  • It works, and it is still there as the opt-out (5g). It needs no context change at all.
  • It costs one graph call, one wait and one 200058-wide logits copy per proposal, per round.
  • The in-graph path replaces D + 1 calls with one and returns only IDs, plus q when sampling.

DFlash2 or LiliCorr style lattices

  • They precompute scores for k candidates per row and let the host walk them. That works because their heads score pairs of candidates.
  • The Inkling head carries a 256-wide state through every step and corrects the hidden row itself. Its output for step i is not a function of a pair of candidates, and the sidecar has no selector or scorer weights.

8. Evidence and open questions

CPU What earlier runs showed

The PR head equals the privately tested candidate patch plus the independent test-file edit: a diff of the two, ignoring index lines, shows only tests/test-backend-sampler.cpp. The runs used the ordinary server on CPU, an IQ4_NL Inkling 2 Mini target, and Q8_0 and BF16 sidecars.

  • Greedy: both sidecars reproduced the target-only server's 32 output tokens.
  • Sampled: an observer matched every q row bit for bit at the verifier and checked that non-argmax draws reached the next W1 lookup (849 complete rows, 355 non-argmax feedback edges across the two main runs).
  • Mixed greedy and sampled slots, different seeds and temperatures, repeated requests, depths 1 to 7 and the host opt-out passed.
  • One scheduled graph per block, and only ID and q copies came back.

The results above come from earlier CPU runs.

unverified What no run has covered

  • Accelerator placement. The graph asks for the draft's output device for selection nodes the backend supports; the scheduler may still put any of them on CPU. Where they land on a GPU is unobserved.
  • Accelerator correctness. Ticket and q agreement, tie-breaking and real-weight feedback on a GPU.
  • Speed. Runtime and speedup for the in-graph path remain unmeasured. An earlier CPU probe measured 1.56 ms per proposal for host sampling and bookkeeping on the stepwise prototype.
  • Numerical parity with an independent runtime, end to end.
  • The non-looped Inkling 2 target, context shifts, saved and restored slots, and vision input. The ring has no serialisation; a slot whose ring lacks pos0 − 1 simply does not draft.

Read from source, not run

Every flow for the older drafters in sections 2 to 4 is a reading of the code at the head commit. Stock DSpark's DeepSeek and Mistral backbones are named but not traced.
